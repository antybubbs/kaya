# High Availability

Kaya High Availability is a resilience framework for supported providers and applications. Each integration defines its own topology, health checks, configuration controls and recovery actions. Pi-hole is the first Beta integration; High Availability is not limited to DNS services.

## How Kaya fits into your service

Kaya is the management plane. It helps you configure, validate and observe the cluster, but it is not in the path used by clients. A deployed service continues locally when Kaya is offline.

For Pi-hole, two small node agents perform only fixed, signed and generation-checked HA actions. The agents and the local failover service continue monitoring the nodes without Kaya. A recovered node returns as standby; Kaya does not automatically move service back to the preferred node.

## Pi-hole deployment modes

### DNS only

Choose this when a router, pfSense, OPNsense, UniFi, Windows Server or another platform provides DHCP.

Configure that DHCP service—and any statically configured clients—to use the **DNS Virtual IP** as their DNS server. The address remains the same while Kaya’s local failover configuration moves it between healthy Pi-hole nodes.

### DNS + DHCP

Choose this when Pi-hole provides IP addresses as well as DNS.

DHCP clients must receive the **DNS Virtual IP** as their DNS server. Do not
advertise either Pi-hole node’s physical address as primary or secondary DNS:
clients may select either address and bypass the shared service. If a DHCP
interface requires a second DNS entry, leave it empty rather than entering a
node address.

When roles change, the DNS Virtual IP moves to the new active node. DHCP may run only on the node that owns that address. Lease snapshots and reservations are prepared on the standby so that failover does not depend on Kaya being online.

After changing the advertised DNS address, existing DHCP clients retain their
old option until their next renewal. Renew each client once, or allow the
existing lease period to expire. Kaya’s logical HA provider reads recent query
activity from both reachable nodes during this transition and stores it under
the same DNS Manager provider history.

## Guided setup

1. Enable **High Availability (Beta)** in Site Administration.
2. Select **Create cluster**, then choose the provider or application. Pi-hole is the available Phase 1 integration.
3. Choose **DNS only** or **DNS + DHCP**.
4. Enter both node API addresses and application passwords.
5. Enter each node’s client-network interface, the DNS Virtual IP, network prefix and gateway.
6. Test both read-only connections and review the architecture summary.
7. Save the cluster, install an agent on each node and run validation.
8. Resolve every blocking readiness check before deploying the shared DNS address.
9. Review configuration differences, synchronise supported settings and test a controlled failover.
10. Enable automatic failover only after the controlled test succeeds.

The DNS Virtual IP must be unused, unique in Kaya and on the same Layer 2 IPv4 network as both nodes. Both Pi-holes must run the same supported major/version combination.

## Day-to-day operation

Use **Overview** for current ownership, node health, synchronisation state, alerts and failover. Operational cards update automatically.

- **Nodes** manages provider connections and network interfaces.
- **Sync** compares supported configuration from the authoritative node to the target, then backs up, applies, verifies and rolls back if needed.
- **DHCP** is active only for DNS + DHCP clusters. DNS-only clusters leave their external DHCP service untouched.
- **Activity** retains agent, failover and safety events.
- **Failover** shows controlled and automatic transition history.
- **Setup & maintenance** contains validation, agents and shared-address deployment details.

## Recovery and controlled failback

Kaya follows: **fail over quickly, recover carefully, fail back deliberately**.

After an automatic failover, the surviving node remains the current active node. The original preferred node progresses through **Offline**, **Recovering**, **Synchronising**, **Verifying**, and **Standby — Ready**. It cannot be offered for failback until:

- its signed HA Agent heartbeat, local DNS, failover service, interface, identity, and cluster generations are current;
- a post-recovery comparison or synchronisation from the current active node has completed without supported drift;
- DHCP configuration, lease staging, and generation checks pass for DNS + DHCP clusters; and
- those checks remain healthy for the stability window.

Kaya never performs automatic failback by default. When the recovered preferred node is ready, an administrator can approve a controlled failback. Kaya performs one final sync, reuses the same guarded handover and rollback engine, and keeps or restores the known-good active node if a safety check fails.

Connection Diagnostics reports three independent signals:

- **Peer Kaya heartbeat** confirms whether the peer has recently sent a signed heartbeat to Kaya.
- **Peer DNS service** tests whether the peer accepts a TCP connection on DNS port 53.
- **Peer Network Reachability** is an optional ICMP ping only.

**Ping unavailable** is informational. ICMP is commonly blocked by a host firewall or network, so this result never marks a node offline, degrades an otherwise healthy cluster, blocks failover or failback, or implies that DNS or an HA Agent has failed.

**ICMP probe unavailable** means the node could not execute the local ping probe, usually because the installed agent service capability or ping package needs repair. Update or reinstall the agent to reconcile its non-root systemd service. Kaya still evaluates signed heartbeats, DNS health, and failover independently.

Existing clients may temporarily display the previous DHCP server until they acquire a new lease. This does not mean that the previous Pi-hole is still serving DHCP; Kaya determines ownership from current HA service state.

## Understanding live service state

Kaya treats the HA Agent's latest signed observation as evidence, not as an instruction result. A successful "enable DHCP" or "disable DHCP" response means the node accepted the action; Kaya waits for a newer observation before declaring the service active or released.

For DNS + DHCP clusters, the live state combines four independent facts:

- whether Pi-hole is configured to provide DHCP;
- whether Pi-hole FTL is active;
- whether UDP port 67 is listening; and
- when that observation was made.

Kaya keeps **DHCP configuration** and **DHCP runtime** separate. For example,
`dhcp.active=false` with a healthy FTL process listening on UDP/67 means the
service is running but its saved Pi-hole setting has drifted. Kaya reports the
real service as available and the configuration as inconsistent; it does not
mislabel that node as stopped.

If any probe cannot be completed, Kaya displays **Unknown — probe unavailable**. It does not silently turn an unknown result into **Stopped**, start DHCP on another node, or declare a transition complete. Signed reports carry a monotonic sequence number so a delayed report cannot overwrite newer runtime truth.

The overview separates **Service availability**, **Redundancy**, and **Control plane**. A surviving active node can continue serving DNS and DHCP while its peer is off; in that case service may remain healthy while redundancy is reduced. Reinitialisation observes the current topology first. If the requested owner already exclusively holds the Virtual IP and DHCP, Kaya repairs its stored roles and recovery metadata without moving service.

During a controlled handover, the live progress panel shows persisted stages, elapsed time, and actual verification attempts. Refreshing or reopening the page resumes the same server-side run; the browser does not invent progress from a timer.

### Automatic topology reconciliation

Kaya observes each fresh signed Agent report and also runs a lightweight
periodic watchdog. It compares the real two-node topology with these DNS + DHCP
invariants: one Virtual IP owner, one UDP/67 owner, DHCP configuration enabled
on that owner, DHCP configuration disabled on the standby, and healthy DNS.

If ownership is unambiguous and only the Pi-hole DHCP setting has drifted, Kaya
uses the existing restricted Agent helper to correct that setting once, waits
for a newer signed report, and records the repair in Activity and Audit history.
The live overview shows the real repair stage and elapsed time. A failed repair
enters a cooldown instead of repeatedly toggling DHCP.

Kaya never guesses in a split-brain, dual-DHCP, stale-telemetry, unknown-owner,
or concurrent-transition state. Those cases remain blocked and require review.
During a proven local hard failover, the surviving Agent's signed completion
event can establish that the failed peer is offline; Kaya may then repair DHCP
configuration on the sole Virtual IP owner without moving the Virtual IP.

## Beta verification checklist

Use non-production nodes and an unused Virtual IP for this test. Replace the example values with addresses from your test network.

1. Confirm both agents show version **0.2.8** or newer, are live, and report fresh DNS and DHCP observations.
2. On each node, confirm Keepalived is running and only one node owns the Virtual IP: `ip -4 address show dev <interface>`.
3. Query the shared address directly: `dig @<virtual-ip> example.com` or `nslookup example.com <virtual-ip>`.
4. For DNS + DHCP, renew a test client lease and confirm its DNS server is the Virtual IP—not a physical Pi-hole address.
5. Run a controlled failover. Follow the server-derived stages and confirm exactly one Virtual IP owner and exactly one UDP/67 listener after completion.
6. Run controlled failback only after the recovered preferred node is stable and Kaya marks it ready.
7. Power off the active test node. Confirm local automatic failover works while Kaya is online, then repeat with Kaya unavailable. Network service must remain local to the Pi-holes.
8. Restore the node and confirm it returns as standby. Check that service availability remains healthy while redundancy moves from reduced back to healthy.
9. In DNS Manager, query the HA provider through the Virtual IP and confirm existing provider history and linked IP data remain present.
10. Review **Activity** and the downloaded HA report for the signed observations, ownership change, retries, and final topology. No registration token, API password, lease payload, or other secret should appear.

## Safety and data retention

- Unknown or ambiguous high-risk state blocks deployment or DHCP activation.
- Split-brain evidence blocks automatic DHCP promotion.
- Secrets are encrypted and never displayed again.
- Provider writes use allowlisted operations, backup-before-write, read-back verification and rollback.
- Removing a cluster is a soft deletion. Stored nodes, DNS Manager links, linked IP details, validation records and history remain unless the user explicitly deletes data in the module that owns it.
- A healthy Pi-hole HA cluster can be selected in DNS Manager as one logical provider through its DNS Virtual IP. Standalone Pi-hole providers continue to work as before.

## Future integrations

Future providers and applications may use different node counts, service-address mechanisms, agents, validation checks or recovery strategies. Pi-hole-specific pages and language appear only when the Pi-hole integration is selected; the framework, navigation and permission model remain provider-neutral.
