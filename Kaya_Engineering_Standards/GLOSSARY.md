# Kaya Glossary

**Audit event**  
A durable record of a security-relevant or user-relevant action.

**Background service**  
A long-running or scheduled task started by Kaya, such as monitoring, polling, cleanup or reconciliation.

**Category**  
A user-managed classification applied to supported records within a module.

**Custom field**  
A user-defined data field attached to record types that explicitly support custom fields.

**Global role**  
The broad application role assigned to a user, currently expressed through roles such as administrator, editor and viewer.

**Host**  
A managed endpoint or system represented within a Kaya module. The precise capabilities depend on the module.

**Known client**  
A DNS or network client identity that Kaya should retain and reconcile across address changes.

**Module**  
A cohesive Kaya feature area with its own routes, views, permissions and domain behaviour.

**Module access**  
The set of enabled Kaya modules a user may enter, in addition to the actions permitted by the user's global role.

**Observation**  
A time-stamped operational finding or note associated with monitored infrastructure.

**Peer**  
Another node or service participating in a redundancy or synchronisation relationship.

**Service layer**  
Application code that owns reusable business rules and multi-step operations outside route handlers.

**Site Administration**  
The protected Kaya area for global configuration, security, modules, integrations and system behaviour.

**Source of truth**  
The authoritative record used to resolve conflicting representations. The engineering source of truth is `KAYA_ENGINEERING_STANDARDS.md`.

**Stale data**  
Data that was previously valid but has not been refreshed within its expected interval.

**VIP**  
A virtual IP address used to provide a stable network endpoint across redundant systems.

**Wallboard**  
A read-focused monitoring display intended for continuous or shared presentation, with access controls appropriate to the data shown.
