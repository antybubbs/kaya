# Kaya v0.27 Release Validation

**Validation date:** 2026-08-04

**Release branch:** `dev0.27.0`

**Validated merged baseline:** `b85bbd3c1b0128c607f1eaf7a0518f2ed53975b3`

**Released Docker Agent:** `ghcr.io/antybubbs/kaya-docker-agent:v0.2.1` (digest `sha256:f18da53a22b8ee74897717f955dcce646edac2beb72a9c8ebd2bc0c5ce01c13a`, source revision `ed9e30da3fd18acdb871767b9ba89728dbbc731b`)

## Executive summary

**Release recommendation: Ready with observations.**

The merged v0.27 security stack passed the complete automated test suite, static validation, focused migration/protocol testing, clean-image construction, clean database creation, repeated startup, online backup, isolated restore and HTTP authentication smoke testing. The released Docker Agent image is available and identifies the reviewed merged source revision.

One release blocker was found during installer validation: `install-kaya.sh` generated an incomplete deployment without the Secure Send gateway or guacd and removed the `NET_RAW` capability required by the supported stack. The release hotfix aligns the generated deployment with the reviewed Compose topology. Its rendered Compose file was validated and the resulting three-service stack was started successfully.

Release status documentation also contained stale pre-merge protocol-v2 language and non-final ADR statuses. These statements were corrected as part of the same release hotfix. No application feature, architecture, deferred High finding or cosmetic behavior was changed.

### Installation, startup, upgrade and restore

- Built a fresh local image from the release baseline with `APP_VERSION=0.27.0-rc-validation`.
- Started the image with empty isolated data/upload volumes, a read-only root filesystem, `no-new-privileges`, `NET_RAW` and a `noexec,nosuid` temporary filesystem.
- `/healthz` returned HTTP 200. Startup upgraded a fresh database through every Alembic revision to `20260804_03` without an error or traceback.
- Restarted the container and confirmed the one-way hash of `.runtime.env` remained unchanged; the container returned healthy with zero restarts.
- Created an online SQLite backup. `PRAGMA integrity_check` returned `ok` for the source and backup.
- Restored the backup, together with its original runtime key material, into a separate volume and instance. The restored application returned healthy at revision `20260804_03`; its integrity check returned `ok`.
- The focused migration suite covered fresh creation, reconstructed supported historical upgrades, repeated startup, validation failures, backup reuse/restoration and intentionally blocked unsafe downgrade boundaries.
- Executed the repaired installer in an isolated Linux environment, rendered its output with Compose, and started Kaya, Secure Send and guacd. Kaya was healthy, Secure Send was running and correctly denied an unauthorised health request, guacd was reachable from Kaya on TCP 4822, and all services had restart count zero.

- Confirmed the login form supplied CSRF state, a valid login reached an authenticated route, the session cookie was HttpOnly, logout returned to `/login`, and a protected route redirected to `/login` after logout.

## Functional validation summary

### Authentication

The complete suite covers login failure/success policy, logout, durable session expiry/revocation, password reset, OIDC login and administrator linking, fresh-authentication binding, invitation consumption/revocation, RBAC, module permissions, CSRF, proxy-aware secure-cookie behavior and redacted audit events. Manual disposable-instance login/logout and post-logout denial also passed. A real identity-provider round trip remains a deployment acceptance check.

### Remote Manager

SSH/RDP permission and audit regressions passed in the complete suite. The focused RDP trust tests validate system-CA trust, explicit SHA-256 pins, rotation/invalidation and rejection of unknown, changed, expired or mismatched certificates. Revision `20260804_02` retains invalidation evidence and blocks an insecure downgrade. `KAYA-RDP-001` remains High and open; this validation did not change it.

### Backup Agent

Enrollment, signing-key and encryption-key ownership, rotation, revocation/decommission, signed polling, scoped claims, encrypted envelopes, durable replay rejection, backup/restore dispatch state, protocol-v1 migration and post-cutoff rejection passed synthetic protocol and security tests. Shared vectors reproduce in Kaya and the agent, and direct server-to-agent envelope interoperability passes. The published v0.2.1 image was pulled successfully and its OCI source revision is the merged agent commit. Operators must still perform an environment-specific backup and restore with their actual storage target before production cutover.

### Secret management

Secret Vault and Secure Send authentication, ownership, permission, CSRF, encryption, output minimisation and audit regressions passed. Persistent key loading survived restart, and the database/key restore ceremony succeeded. Rotation paths are covered by automated tests; operational rotation should retain a verified recovery copy.

### HA and notifications

The existing HA and notification suites passed as part of the complete run. Startup and short runtime observation showed no scheduler or notification-runtime regression. No HA redesign or deferred finding remediation was attempted, and no live failover or delivery provider was exercised.

### Database and packaging

Fresh migration, historical upgrade, schema validation, backup, restore and integrity checks passed. Security migrations deliberately refuse unsafe downgrade across RDP and protocol-v2 boundaries; rollback is therefore an operational restore/roll-forward procedure, not an Alembic downgrade through those boundaries. The Dockerfile, supported Compose file, repaired installer, environment defaults and entrypoint were validated. No image was published by this review.

### Documentation

README, deployment/installation and upgrade guidance, backup-agent protocol/operations guides, Remote Manager/RDP trust guidance, release notes, Engineering Standards and ADR directory were reviewed. The release hotfix corrects stale protocol-v2 merge status, the findings summary, remediation status, accepted ADR states and the previously missing ADR index entries.

## Security summary

All tracked Critical findings are resolved in the reviewed implementation:

- `KAYA-DEM-001` and `KAYA-DEM-002`: public demo and demo-mode functionality removed.
- `KAYA-OIDC-001`: recipient-bound administrator linking and fresh-authentication controls merged.
- `KAYA-RDP-002`: strict RDP certificate validation and pin lifecycle merged.
- `KAYA-BAK-001`: coordinated protocol-v2 server and genuine Docker Agent implementation merged; released agent v0.2.1 is available.

No new Critical or High issue was identified by this validation. Direct dependency audits reported no known vulnerabilities at validation time.

## Known limitations

- External-system behavior was not tested against live OIDC, SSH, RDP, HA, notification or backup infrastructure.
- The released agent image is tagged `v0.2.1` and points to the correct source revision, but its OCI version label contains `latest`; this is provenance metadata debt, not a runtime mismatch.
- Guacd 1.6.0 declares a five-minute healthcheck interval, so Compose can display `health: starting` even while TCP 4822 is already reachable.
- The complete suite produces substantial framework deprecation warnings. These should be reduced before adopting Python 3.13 or later FastAPI/SQLAlchemy releases.
- Requirements are pinned but not fully hash-locked.

## Deferred findings

The following accepted High risks remain open and are accurately disclosed in the v0.27 release notes:

- `KAYA-RDP-001` — credential-bearing RDP connection data in WebSocket query data.
- `KAYA-HA-001` — Keepalived transition lock held during hold-down and slow probes.
- `KAYA-BG-001` — HA watchdog/lease outer-loop exceptions can terminate background tasks.
- `KAYA-DB-001` — inconsistent SQLite connection policy and incomplete contention qualification.

These findings were not remediated or redesigned during release validation.

## Upgrade notes

- Back up the database, uploads, recordings and the original `ENCRYPTION_KEY` before upgrade; test that the local break-glass administrator works.
- Existing unused pre-binding OIDC invitations are revoked by migration. Issue new invitations after upgrade.
- RDP hosts using self-signed/private certificates require an independently verified SHA-256 pin. Do not restore connectivity by enabling bypass or trust-on-first-use.
- Upgrade Docker agents to released v0.2.1, protect their state volume, remove bootstrap tokens after enrollment and complete the fixed protocol-v1 migration window.
- Use local supported storage and one Kaya application process while `KAYA-DB-001` remains open.

## Rollback notes

- Preserve the pre-upgrade database, uploads, recordings and matching original `ENCRYPTION_KEY` as one recovery set.
- Downgrade below database revision `20260804_02` is intentionally blocked to prevent restoration of universal RDP certificate bypass.
- Downgrade below `20260804_03` is intentionally blocked to prevent restoration of bearer-token secret delivery.
- If either boundary causes an operational failure, stop the affected RDP or backup dispatch function, preserve queued work and roll forward to a security-equivalent build. Do not re-enable the insecure v1 secret-delivery path.

## Remaining technical debt

- Replace deprecated UTC datetime, FastAPI lifespan and passlib integration paths before their upstream removal dates.
- Produce fully hash-locked dependency inputs and retain automated dependency/container/SBOM checks.
- Correct the Docker Agent OCI version label on the next agent packaging update.
- Run deployment-specific acceptance exercises for real identity, remote-access, notification, HA and backup providers.
- Address the four deferred High findings in separately reviewed work after v0.27.

## Security Impact

- **Security-sensitive components:** Release packaging and security-status documentation were changed; application authentication, authorisation, cryptography, protocol and database code were not modified.
- **Authentication and authorisation:** The installer now deploys the same authenticated Kaya, isolated Secure Send gateway and guacd topology as the supported Compose file. No role, permission, session or object-authorisation rule changed.
- **Input validation and trust boundaries:** Installer-controlled image and environment substitutions remain bounded by the existing shell/Compose interface. The public Secure Send service retains its restricted route, host, origin and health-token controls.
- **Secrets and personal data:** Only synthetic credentials and isolated data were used. Secret values, setup tokens and decrypted application data were not recorded. Backup/restore preserved key material without displaying it.
- **Tests:** Full pytest, focused protocol/migration tests, Ruff, Node syntax, dependency audits, Compose rendering, clean install, restart, backup/restore, integrity, HTTP authentication and multi-service installer startup all passed.
- **Remaining risks and assumptions:** The four deferred High findings, external-provider acceptance, deprecation debt, unhashed dependency pins and agent version-label observation remain as documented above.

## Final recommendation

The validated release hotfix is integrated into `dev0.27.0`. Tag and publish only through the normal human-controlled release process. No merge to `main`, GitHub release creation or image publication was performed during this validation.
